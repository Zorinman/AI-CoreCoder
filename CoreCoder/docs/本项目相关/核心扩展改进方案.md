# CoreCoder 核心扩展改进方案

## 范围与现状

本方案覆盖以下三个扩展方向：

1. 备用模型。
2. 基于工具副作用的并发调度。
3. MCP 工具接入。

当前代码已具备同一轮多个工具调用的并行能力：`Agent._exec_tools_parallel()` 使用最多 8 个线程执行全部调用，并按模型给出的原始顺序写回工具结果。问题不在于没有并发，而在于 `Tool` 没有副作用元数据，读、写、Bash 和子 Agent 都会被同时提交。`LLM` 当前只有一个模型端点；MCP 也尚未作为工具来源接入。

## 总体决策

保留现有同步 `Tool.execute()` 和 `Agent.chat()` 的外部接口，在内部增加两个明确边界：

- 工具执行边界：每个工具声明只读或独占执行；默认独占。
- 模型调用边界：路由器在可安全重试且尚未产生输出时切换备用端点。

MCP 工具通过适配器实现现有 `Tool` 接口，不修改 Agent 的消息协议。这样，OpenAI 兼容函数调用、上下文压缩、工具结果顺序和会话主循环保持不变。

```text
CLI 配置
  -> ModelRouter -> LLM / LiteLLM 端点
  -> MCPManager  -> MCPTool[] ---+
内置 Tool[] ---------------------+-> Agent 工具注册表 -> 副作用调度器
```

## 一、备用模型

### 1.1 配置模型

引入 JSON 配置文件作为多端点配置的唯一来源，并保留现有 `.env` 用于保存密钥。配置文件只引用环境变量名，不保存 API Key。CLI 新增 `--config` 指定配置文件。

```json
{
  "models": {
    "primary": {
      "id": "main",
      "provider": "openai",
      "model": "gpt-5.5",
      "api_key_env": "OPENAI_API_KEY",
      "base_url_env": "OPENAI_BASE_URL"
    },
    "fallbacks": [
      {
        "id": "backup",
        "provider": "litellm",
        "model": "openai/gpt-5.4-mini",
        "api_key_env": "OPENAI_API_KEY"
      }
    ]
  }
}
```

配置加载后转换为以下项目内对象：

```python
from typing import Protocol

@dataclass(frozen=True)
class ModelEndpoint:
    id: str
    provider: str
    model: str
    api_key: str
    base_url: str | None

class ModelClient(Protocol):
    model: str
    total_prompt_tokens: int
    total_completion_tokens: int

    @property
    def estimated_cost(self) -> float | None: ...

    def chat(self, messages, tools=None, on_token=None) -> LLMResponse: ...

class ModelRouter:
    def chat(self, messages, tools=None, on_token=None) -> LLMResponse: ...
```

`LLM`、`LiteLLM` 和 `ModelRouter` 都满足 `ModelClient` 协议。`Agent` 的类型标注改为该协议，但 `chat()` 的调用方式不变。`ModelRouter` 公开 `model`、累计 Token 和 `estimated_cost`，使 `/tokens` 与其他既有调用方不依赖底层端点类型。

### 1.2 备用模型切换

`ModelRouter` 按“当前成功端点、其余候选端点”的顺序调用。每个端点先完成其自身的指数退避重试；只有下列条件同时成立时才尝试下一个端点：

- 错误属于限流、连接、超时或服务端 5xx/529。
- 本次流式响应尚未向 `on_token` 发送任何文本，也未形成工具调用结果。

OpenAI 和 LiteLLM 需要先将各自异常映射为内部的“可重试”与“不可重试”类别，再交给路由器判断；不能依赖 LiteLLM 的异常文本进行跨 provider 决策。认证、权限、请求参数、工具 Schema 等 4xx 错误直接失败，不能切换模型。流式输出开始后的错误也直接失败，避免用户已经看到部分内容后自动重新执行并产生重复工具操作。

当前 `LLM.chat()` 只有在完整收集流式响应后才返回 `LLMResponse`，Agent 随后才会写入 assistant 消息并执行工具。因此，若流式过程出现异常但从未调用外部 `on_token`，即使内部已收到不完整的工具调用增量，也可以切换备用端点：未返回的工具调用不会被执行。若已经向外部发送任意文本，则直接失败。

备用端点成功后成为本会话的当前端点；用户显式 `/model` 切换或重新启动会话时才重置选择。`/model` 只能选择已配置的端点 ID，不能再直接为底层对象赋任意模型字符串。

模型端点由工厂创建 `LLM` 或 `LiteLLM`，因此跨 provider 的备用关系必须在配置中逐项声明，而不是依据模型名猜测。现有 `/tokens` 保持累计 Token 与估算成本的显示行为，不参与备用模型切换决策。

会话 JSON 增加可选字段 `model_route.active_endpoint_id`。恢复会话时，CLI 调用 `ModelRouter.restore_endpoint()` 恢复已成功切换的端点，不能直接设置 `agent.llm.model`。旧会话没有该字段时，以保存的 `model` 匹配已配置端点；无匹配项则使用主端点并显示提示。会话保存、加载与列表函数相应返回带路由状态的会话对象，并兼容没有该字段的旧 JSON。

## 二、读写感知的并发策略

### 2.1 工具元数据

在 `corecoder/tools/base.py` 增加执行模式，默认值必须是最保守的 `EXCLUSIVE`：

```python
from enum import Enum

class ExecutionMode(str, Enum):
    READ_ONLY = "read_only"
    EXCLUSIVE = "exclusive"

class Tool(ABC):
    execution_mode = ExecutionMode.EXCLUSIVE
```

内置工具的初始分类如下：

| 工具 | 模式 | 原因 |
| --- | --- | --- |
| `read_file`、`glob`、`grep` | `READ_ONLY` | 不修改工作区或进程状态。 |
| `write_file`、`edit_file` | `EXCLUSIVE` | 可能写入同一文件或依赖读取时刻。 |
| `bash` | `EXCLUSIVE` | 命令语义不可静态可靠判定，且会维护工作目录状态。 |
| `agent` | `EXCLUSIVE` | 共享模型、当前端点状态和父 Agent 的执行资源。 |
| `MCPTool` | `EXCLUSIVE` | 仅在本地显式标记或服务器可信 `readOnlyHint` 为真时降为只读。 |

第三方工具没有声明该字段时自动使用默认独占模式，避免因为遗漏标注而引入数据竞争。

### 2.2 调度规则

将当前“全部提交线程池”改为按模型原始顺序扫描的批处理调度：

1. 收集连续的 `READ_ONLY` 调用，最多以 `max_parallel_tools` 个线程并行执行。
2. 遇到一个 `EXCLUSIVE` 调用时，先等待前一个只读批次完成，再在 Agent 主线程执行该调用。
3. 继续扫描后续调用，直到本轮结束。
4. 无论实际完成次序如何，始终以原始 `tool_calls` 顺序写入 `messages`。

例如 `read_file(A), grep(B), edit_file(A), read_file(A)` 会先并行读取和搜索，再编辑 A，最后读取修改后的 A。`max_parallel_tools` 默认保留为 8，可通过配置调整。所有 `on_tool` 回调在工具实际开始前触发。

`bash` 退出线程池后会在 Agent 主线程执行，当前 `threading.local()` 中保存的工作目录能够在相邻串行 Bash 调用之间保持一致；同时不会与写文件、编辑文件或子 Agent 发生并发竞态。

### 2.3 验收测试

新增可控的假工具和事件记录，覆盖以下场景：

- 两个只读工具的运行时间重叠，结果仍按调用顺序返回。
- 写工具不会与任何同轮调用重叠；两个写工具按模型给出的顺序执行。
- 只读、写入、只读的混合序列保持三个批次的先后关系。
- 未声明执行模式的工具默认串行。
- 一个工具返回错误或抛出异常时，其他结果仍与正确的 `tool_call_id` 配对。
- Ctrl+C 后依旧为尚未写回的调用补充 `[interrupted]` 工具消息。

## 三、MCP 接入

### 3.1 第一阶段范围

第一阶段仅支持由用户本地配置启动的 stdio MCP server，不自动发现 server，不从提示词、仓库文件或网络下载配置。远程 HTTP/SSE transport、资源订阅、prompt 模板和 MCP sampling 延后实现。这样可先控制最重要的边界：启动外部进程和执行其暴露的工具。

配置文件增加 `mcp_servers`：

```json
{
  "mcp_servers": {
    "filesystem": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-filesystem", "/workspace"],
      "env_allowlist": ["HOME"],
      "required": true,
      "read_only_tools": ["list_directory", "read_file"]
    }
  }
}
```

在 `pyproject.toml` 中新增可选依赖组 `mcp`，安装后才启用该功能。未安装依赖而配置了 `required: true` 的 server 时 CLI 以明确错误退出；非必需 server 记录警告并不注册其工具。

启动前还要验证 server 名称唯一、`command` 可在受控 PATH 中解析、参数为字符串列表、超时为正数。示例中的 `npx` 只是一个 server 启动器，实际运行环境必须显式具备 Node.js 与目标 server 所需的运行时。

### 3.2 适配与生命周期

新增 `corecoder/mcp.py`，其中包含：

- `MCPServerConfig`：解析、验证 command、args、允许传递的环境变量和超时。
- `MCPManager`：在 CLI 创建 Agent 前连接 server、初始化会话、获取工具列表，并在退出时关闭全部会话和子进程。
- `MCPTool(Tool)`：保存 server 名、原始工具名、输入 JSON Schema 和执行模式；`execute()` 将参数转发给 `MCPManager.call_tool()`，再把文本或 JSON 结果转换为字符串。

MCP Python SDK 的异步会话由 `MCPManager` 专有的事件循环线程持有；同步 `MCPTool.execute()` 使用线程安全 future 等待结果。一个 server 的调用通过该 manager 串行化，除非后续明确验证该 server 支持并发请求。Agent 因而无需改为异步，也不会在每次工具调用时反复启动或初始化 server。

向模型暴露的工具名使用稳定命名空间：`mcp__{server}__{tool}`。名称中的非法字符被规范化，过长名称以稳定短哈希截断；manager 保存“公开名到原始 server/tool 名”的映射。输入 Schema 必须是顶层 `object`；不满足 OpenAI 函数调用约束的工具不注册，并在启动报告中说明原因。

`ALL_TOOLS` 保持为不含 MCP 的内置工具集合，不能在运行时被修改。新增 `build_tools(mcp_manager=None)`，每次创建 Agent 时产生新的内置工具实例，并在传入 manager 时追加 `MCPTool`。CLI 使用该工厂并显式传入 `tools` 创建主 Agent；子 Agent 继续复用父 Agent 的工具列表。这样，多个 Agent、测试和不同 MCP 配置之间不会共享错误的 server 绑定。

CLI 在 MCP manager 创建完成后以 `try/finally` 运行 REPL 或单次请求，`finally` 中调用 `MCPManager.close()`，确保 Ctrl+C、模型异常或普通退出都会关闭会话、事件循环和 server 子进程。

### 3.3 安全与故障边界

- MCP server 只允许来自用户显式配置。`command`、`args` 和工作目录不接受模型工具参数覆盖。
- 继承环境变量时采用白名单，API Key 等敏感变量必须逐个允许传递；日志不得打印变量值。
- MCP 工具默认独占。只有 `read_only_tools` 本地白名单中的工具才允许并发；`readOnlyHint` 只能用于提示用户或校验配置，不能单独构成并发安全依据。
- 工具调用使用独立超时、输出长度上限和 UTF-8/JSON 安全转换。调用失败返回普通工具错误文本，从而保持现有 assistant/tool 消息配对。
- server 启动、Schema 获取和调用失败均不触发模型 fallback；它们不是 LLM provider 故障。

### 3.4 验收测试

使用假 MCP client 覆盖 server 配置校验、工具发现、名称映射、Schema 拒绝、结果转换、超时、server 关闭和失败隔离。另测试一个只读 MCP 工具可进入并行批次，未标注或写入型 MCP 工具必须串行。

## 四、实施顺序与完成标准

1. 先添加 `ExecutionMode`、分批调度和并发测试，消除当前所有工具盲目并行的正确性风险。
2. 再实现端点配置、标准化错误分类和 `ModelRouter`，补齐可安全 fallback、端点切换、流式失败边界与会话恢复测试。
3. 最后接入 stdio MCP，将 server 工具通过实例级工厂适配到新的执行模式，并完成启动预检、生命周期和安全边界测试。

每个阶段完成后执行完整 pytest 套件，并新增对应的单元测试。完成状态应满足：不安全工具不重叠执行；MCP server 无法从模型输入中被任意启动或改写；所有工具结果继续与其原始 `tool_call_id` 一一对应；可重试且未产生输出的模型故障会按配置切换到备用端点。

## 五、明确不在本次范围内的能力

- 流式生成期间的投机式工具执行。
- 对部分流式输出失败后的自动模型切换。
- 自动发现、自动安装或由模型动态添加 MCP server。
- 对远程 MCP server 的认证、重连与多 transport 支持。
