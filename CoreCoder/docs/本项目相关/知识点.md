# 如何自定义项目启动命令

CoreCoder 是一个 Python 包。终端中能直接输入 `corecoder`，不是因为 Windows 认识这个项目目录，而是因为安装工具根据项目配置创建了一个命令行启动器。

## 1. 命令从哪里定义

项目的 [`pyproject.toml`](../CoreCoder/pyproject.toml) 中有：

```toml
[project.scripts]
corecoder = "corecoder.cli:main"
```

这是 Python 打包规范中的命令行入口配置：

```text
命令名                 Python 导入路径和函数
corecoder      ->      corecoder.cli:main
```

- 左侧 `corecoder` 是用户在终端用于启动项目的**自定义命令名**
- 右侧 `corecoder.cli:main` 表示导入 `corecoder/cli.py`，再调用其中的 `main()` 函数。
- `main()` 是项目自行定义的函数；`[project.scripts]` 是打包工具识别的标准配置。

## 2. 安装时发生了什么

在项目根目录执行：

```powershell
python -m pip install -e .
```

`pip` 会读取 `pyproject.toml`，并在当前 Python 环境的 `Scripts` 目录生成命令行启动器。Windows 上通常会看到：

```text
<Python 环境>\Scripts\corecoder.exe
```

`corecoder.exe` 不是 CoreCoder 开发者手写的业务程序。它是 `pip` 根据入口配置自动生成的通用 Windows 启动器，作用是使用当前环境的 Python 调用 `corecoder.cli.main()`。

`Scripts` 只是 Python 约定用于放置命令行启动器的目录。虚拟环境激活后，它的 `Scripts` 目录会被加入当前终端的 `PATH`，因此 PowerShell 输入 `corecoder` 时能够找到 `corecoder.exe`。

```text
输入 corecoder
-> PowerShell 在 PATH 查找 corecoder.exe
-> 启动器调用该环境的 Python
-> Python 执行 corecoder.cli.main()
```

`-e` 表示可编辑安装。启动器仍会生成，但它导入的是当前项目目录中的源码；修改 Python 文件后，通常不需要再次安装。



# 启动后固定执行了哪些事情

终端启动器最终调用的是 [`corecoder/cli.py`](../CoreCoder/corecoder/cli.py) 的 `main()`。它负责准备运行环境和进入相应模式；真正处理模型和工具调用的是 `Agent`。

## 启动流程

```text
corecoder
-> _parse_args() 解析终端参数
-> Config.from_env() 读取 .env 和环境变量
-> 命令行参数覆盖环境变量配置
-> 检查 API Key
-> 创建 LLM 和 Agent
-> 根据参数选择恢复会话、一次性模式或 REPL
```

## 1. 解析命令行参数

`_parse_args()` 使用 Python 标准库 `argparse`，支持：

```text
-m / --model       指定模型
--base-url          指定 API 地址
--api-key           指定 API Key
-p / --prompt      单次提问后退出
-r / --resume ID   恢复保存的会话
-v / --version     输出版本并退出
```
这里`--help`、`--version`在解析阶段就退出，因此不会创建配置、LLM 或 Agent。

`-r`、`-p`等虽然也先被解析，但其实际分支在 LLM 和 Agent 创建后才执行

`argparse` 是 Python 内置标准库；`_parse_args()` 是项目定义的函数。

## 2. 读取配置并确定优先级

`Config.from_env()` 会先调用 `_load_dotenv()`：从当前目录开始向上查找 `.env`，找到后加载其中的环境变量，但不会覆盖已经存在的系统环境变量。

随后读取以下配置：

```text
API Key: CORECODER_API_KEY -> OPENAI_API_KEY -> DEEPSEEK_API_KEY
模型:    CORECODER_MODEL，默认 gpt-5.5
地址:    OPENAI_BASE_URL 或 CORECODER_BASE_URL
```

最后，显式传入的 CLI 参数会覆盖环境变量，例如 `corecoder -m qwen3-max` 的优先级高于 `CORECODER_MODEL`。

如果最终没有 API Key，程序打印错误并以状态码 `1` 退出，不会进入 REPL。

## 3. 创建模型客户端和 Agent

有 API Key 时，`main()` 会：

1. 根据 `CORECODER_PROVIDER` 选择 `LLM` 或 `LiteLLM`。
2. 创建模型客户端，保存模型名、Key、地址、温度和输出 Token 上限。
3. 创建 `Agent`。

`Agent.__init__()` 会固定完成这些准备：

- 使用默认工具列表 `ALL_TOOLS`，其中包括读、写、编辑、搜索、Shell 和子 Agent 工具。
- 建立“工具名 -> 工具对象”的字典，方便模型请求工具时查找。
- 创建空的消息历史和上下文管理器。
- 根据工具列表生成系统提示词。
- 将父 Agent 注入子 Agent 工具。

这些对象只是在启动时准备好；此时尚未调用模型，也没有执行 Shell 或文件修改。

## 4. 根据参数进入不同分支

- 使用 `-r ID`：先从磁盘加载会话历史；找不到会话则退出。
- 使用 `-p "问题"`：调用 `_run_once()`，执行一次 `agent.chat()` 后退出。
- 不使用 `-p`：进入 `_repl()`，等待用户持续输入。



# REPL 在本项目中是如何实现的

REPL 是 `Read-Eval-Print-Loop` 的缩写，即“读取输入、求值处理、输出结果、继续循环”。本项目的 REPL 位于 `corecoder/cli.py` 的 `_repl(agent, config)`。

需要区分两个循环：

```text
REPL 循环：用户输入 -> 分派命令或 Agent -> 显示结果 -> 等待下一次输入
Agent 循环：用户消息 -> 模型 -> 工具调用 -> 模型 -> 最终文本回复
```

前者处理人与终端的交互，后者处理模型完成一个任务所需的多轮工具调用。

## 1. 初始化界面、历史记录和按键

进入 `_repl()` 后，程序使用第三方库 `rich` 显示欢迎面板，使用 `prompt_toolkit` 读取用户输入。

```python
hist_path = os.path.expanduser("~/.corecoder_history")
history = FileHistory(hist_path)
```

上面的代码把输入历史保存到用户主目录中的 `.corecoder_history`。`os.path.expanduser`、`while`、`if` 属于 Python 标准库或语言结构；`FileHistory` 来自第三方库 `prompt_toolkit`。

`FileHistory(hist_path)` 的作用是读取并追加这份历史记录。用户下次启动 CoreCoder 时，可以用上下方向键取回以前输入过的内容；它不保存模型回复或完整会话。

`rich` 是终端美化库。本项目先创建 `Console()`，然后通过 `console.print()` 输出带颜色、面板或 Markdown 格式的内容，例如启动欢迎面板、错误信息和工具调用提示。它只负责显示，不负责读取输入或执行 Agent。

程序还注册了两个按键：

```text
Enter             提交当前输入
Esc + Enter       插入换行，便于输入多行内容
```

## 2. 读取输入

核心是一个 `while True` 循环：

```python
while True:
    user_input = pt_prompt(...).strip()
```

- `while True`：无限循环，直到 `break`。
- `pt_prompt(...)`：显示 `You > ` 提示并等待输入。
- `.strip()`：删除输入首尾的空白字符。
- `EOFError` 或 `KeyboardInterrupt`：用户按 Ctrl+C 或输入结束时，打印 `Bye!` 后跳出循环。
- 空输入：通过 `continue` 直接进入下一轮，不发送给模型。

## 3. 本地斜杠命令

输入以 `/` 开头时，REPL 先在本地处理，而不是交给模型。例如：

```text
/help       调用 _show_help()
/reset      调用 agent.reset() 清空历史
/tokens     输出累计 Token 和估算成本
/model      查看或切换当前模型
/compact    请求上下文管理器压缩历史
/save       保存消息历史和模型名
/diff       显示本次会话修改过的文件
/sessions   列出保存的会话
quit        break，退出 REPL
```

每个分支执行完都会使用 `continue`，所以不会继续进入 `agent.chat()`。未知的斜杠命令会提示错误，避免把操作命令误当成普通问题发送给模型。

这些命令没有单独的命令注册系统，而是直接写在 REPL 的 `while True` 循环中。程序先获得 `user_input`，再用 `if` 判断它是否等于某个命令，或是否以命令前缀开头：

```python
if user_input == "/reset":
    agent.reset()
    continue

if user_input == "/model" or user_input.startswith("/model "):
    # 读取 /model 后的模型名并切换
    continue
```

要新增 `/status` 命令，只需在“普通问题调用 `agent.chat()`”之前新增一个 `if user_input == "/status"` 分支，执行功能后用 `continue` 进入下一轮。

## 4. 普通问题如何显示流式输出

普通文本会执行：

```python
response = agent.chat(user_input, on_token=on_token, on_tool=on_tool)
```

这里使用了两个项目定义的回调函数：

- `on_token(tok)`：模型每返回一段文本就立即 `print`，实现流式显示。
- `on_tool(name, kwargs)`：模型准备调用工具时，使用 `rich` 输出工具名和简短参数。

`Agent.chat()` 接收回调，但不依赖终端界面本身。这使 Agent 可以被 Web 服务或其他程序复用，只需替换两个回调函数来改变显示方式。

## 5. Agent 循环如何结束

`Agent.chat()` 将用户输入加入历史，发送“系统提示词 + 历史 + 工具定义”给模型。若模型要求工具调用，则执行工具并把结果加入历史，再请求模型；若模型返回纯文本且没有工具调用，就返回该文本给 REPL 显示。

为了避免模型无限调用工具，循环最多执行 `max_rounds` 次，默认值为 `50`。


# Agent 核心循环与工具执行

本节对应 [`agent.py`](../CoreCoder/corecoder/agent.py) 和文章 [`01-the-loop_EN.md`](../CoreCoder/article/01-the-loop_EN.md)。介绍 CoreCoder 时，可以将 Agent 概括为：它反复询问模型下一步该做什么；模型要求调用工具时执行工具并回传结果；模型返回普通文本时结束。

以下章节统一回答“某项内容或功能如何设计”，先说明代码如何协作，再给出设计目的、协议约束和实现边界；不将原因拆成第二个问题。

## 1. Agent 初始化与核心循环如何设计

`Agent.__init__()` 先建立一次会话所需的运行状态：

```python
self.llm = llm
self.tools = tools if tools is not None else ALL_TOOLS
self._tool_by_name = {t.name: t for t in self.tools}
self.messages: list[dict] = []
self.context = ContextManager(max_tokens=max_context_tokens)
self.max_rounds = max_rounds
self._system = system_prompt(self.tools)
```

这些字段分别保存模型客户端、当前实例允许的工具、工具名称索引、对话历史、上下文管理器、轮数上限和系统提示词。`tools` 可以由调用者显式传入；未传入时才使用 `ALL_TOOLS`。因此 Agent 从创建时就具备可配置的工具范围，而不是在执行阶段临时决定权限。

`Agent.chat()` 是一次用户请求的入口。它维护的是 Agent 自己的 `messages` 历史，不包含每次请求都会重新拼在开头的 system message。

```text
用户输入
  -> 写入 messages
  -> 按需压缩上下文
  -> 将 system prompt、历史消息、当前 Agent 的工具 schema 发给 LLM
  -> 检查 LLM 响应是否包含 tool_calls
       -> 不包含：保存 assistant 消息并返回文本
       -> 包含：保存 assistant 的 tool_calls
                 -> 执行工具
                 -> 为每个调用写入匹配的 tool 结果
                 -> 按需压缩上下文
                 -> 进入下一轮
```

这里的职责划分是：LLM 负责判断下一步与何时完成；Agent 负责执行、保存协议正确的历史、限制资源，并将执行反馈交还给 LLM。它不是传统的固定 `if/else` 工作流，模型的决策会影响循环次数和工具选择。

## 2. 模型调用轮数上限如何设计

代码使用：

```python
for _ in range(self.max_rounds):
```

实现方式：`max_rounds` 默认是 `50`，`range(self.max_rounds)` 使主循环至多执行 50 轮。达到上限时，`chat()` 返回：

```text
(reached maximum tool-call rounds)
```

设计目的：模型的“完成判断”不是可靠的程序终止条件。上限提供成本和运行时间的确定边界，防止模型重复调用工具、消耗过多 token 或长时间无法收敛。

## 3. 模型可调用工具如何设计

模型不会直接拿到可执行的工具对象。构造 Agent 时，`self.tools` 保存该实例允许使用的工具；`_tool_schemas()` 只将这些工具转换为 OpenAI function calling 所需的 schema，再传给 LLM：

```python
def _tool_schemas(self) -> list[dict]:
    return [t.schema() for t in self.tools]
```

每轮请求还会通过 `_full_messages()` 组装 system message 与历史消息，并将 schema 一同传入 `self.llm.chat(...)`。模型只能根据 schema 提出工具调用请求，不能自己执行 shell 或修改文件；真正的执行权仍在 Agent 的 `_exec_tool()` 中。schema 负责描述“可以请求哪些能力”，本地查找和参数验证负责决定“是否实际执行”。

## 4. 工具调用结果如何写回对话历史

模型返回工具调用后，Agent 先保存包含 `tool_calls` 的 assistant 消息，再执行工具。每个结果都按以下格式追加：

```python
self.messages.append({
    "role": "tool",
    "tool_call_id": tc.id,
    "content": result,
})
```

`tc.id` 将某次调用与它的结果配对。OpenAI 兼容的工具调用协议要求：一条 assistant 消息中有多少个 `tool_calls`，之后就必须有多少条对应 id 的 `tool` 消息。

协议约束：模型 API 需要根据 `tool_call_id` 知道每个结果属于哪次调用。缺少结果或配对错误会使下一次请求的历史不合法，API 可能直接拒绝请求，因此不能只把工具输出拼成一段普通文本。

## 5. 单个工具调用与错误处理如何设计

`_exec_tool()` 的顺序是：

```text
按名称找到当前 Agent 可用的工具
-> 校验调用参数能否绑定到 execute() 的签名
-> 真正执行工具
-> 将错误转换为可返回给模型的文本
```

参数校验使用：

```python
inspect.signature(tool.execute).bind(**tc.arguments)
```

`bind()` 只检查参数是否符合函数签名，不运行工具。这样可以区分两种都可能表现为 `TypeError` 的情况：

| 情况                  | 返回给模型的结果           | 处理方式                   |
| --------------------- | -------------------------- | -------------------------- |
| 当前 Agent 没有该工具 | `Error: unknown tool ...`  | 阻止调用超出实例范围的工具 |
| 工具调用参数不匹配    | `Error: bad arguments ...` | 让模型修正参数后重试       |
| 工具内部执行失败      | `Error executing ...`      | 说明工具运行本身失败       |

设计目的：直接调用 `tool.execute(**tc.arguments)` 后无法可靠分辨 `TypeError` 是模型传错参数，还是工具内部代码抛出的。先验证参数可以将两类失败转换为不同的文本反馈，供模型在下一轮判断如何修正。

## 6. 每个 Agent 的工具范围如何设计

项目有全局工具注册表 `ALL_TOOLS`，它回答“项目一共注册了哪些工具”。但每个 Agent 初始化时，还会建立自己的名称索引：

```python
self._tool_by_name = {t.name: t for t in self.tools}
```

执行时查的是实例索引：

```python
tool = self._tool_by_name.get(tc.name)
```

因此需要区分：

```text
ALL_TOOLS                项目中存在什么工具
Agent._tool_by_name      当前这个 Agent 可以调用什么工具
```

这对受限 Agent 和子 Agent 很重要。子 Agent 创建时会得到裁剪后的工具列表；若执行阶段改为从全局 `ALL_TOOLS` 查找，被裁掉的工具仍会被找回，裁剪只剩下“不给模型看”的作用，无法限制实际执行。

测试 `test_agent_tool_scope_is_per_instance` 验证了该边界：只配置 `read_file` 的 Agent 即使请求一个全局已注册的 `bash`，也会得到 `unknown tool 'bash'`。

注意：这是一层 Agent 内部的能力边界，不是进程级安全沙箱。同一 Python 进程中的其他代码若直接导入全局注册表，仍可能绕开 Agent 的调度路径。

## 7. 子 Agent 的父 Agent 引用如何初始化

初始化时，Agent 会遍历自己的工具；若工具是 `AgentTool`，就写入父 Agent：

```python
for t in self.tools:
    if isinstance(t, AgentTool):
        t._parent_agent = self
```

这样 `AgentTool.execute()` 才能从父 Agent 取得 LLM、工具列表和上下文配置，并创建子 Agent。该反向引用的用途是让“创建子 Agent”这个工具知道自己属于哪个 Agent。

## 8. 多个工具调用如何批量执行

一次 LLM 响应可能包含多个独立工具调用。单个调用直接执行；多个调用进入 `_exec_tools_parallel()`：

```python
with concurrent.futures.ThreadPoolExecutor(max_workers=8) as pool:
    futures = [pool.submit(self._exec_tool, tc) for tc in tool_calls]
    return [f.result() for f in futures]
```

实现要点：

- 调度前会遍历全部 `tool_calls` 并触发 `on_tool(tc.name, tc.arguments)`；这一步用于报告即将执行的工具，不在工作线程中运行。
- 最多同时运行 8 个任务，避免为大量调用无限创建线程。
- `pool.submit()` 返回 `Future`；`f.result()` 会等待对应任务完成并取得结果。
- 虽然任务完成顺序可能不同，结果列表仍按模型原始调用顺序返回，因为 `futures` 按输入顺序保存和读取。
- 对于普通工具异常，`_exec_tool()` 已将异常转换为错误字符串；因此大多数工具失败会成为模型可读的结果，而不是中断整个批次。

当前实现没有给工具标记“可否并发”。因此它适合独立的读、搜索等任务；若多个工具同时修改同一文件或共享可变状态，调用方需要意识到可能发生竞争。这是简化实现的边界，不应将所有工具调用都假定为并发安全。

## 9. 实时输出和工具状态如何设计

`chat()` 接受两个可选回调：

```python
def chat(self, user_input: str, on_token=None, on_tool=None) -> str:
```

| 回调                       | 调用时机           | 用途                       |
| -------------------------- | ------------------ | -------------------------- |
| `on_token(tok)`            | LLM 流式生成文本时 | 终端或 Web UI 逐段显示回答 |
| `on_tool(name, arguments)` | 工具即将执行时     | 显示工具名、参数或记录日志 |

`on_token` 被转交给 `self.llm.chat(...)`，由 LLM 的流式响应触发；`on_tool` 在工具执行前由 Agent 触发。它们由 CLI 或其他调用者传入，Agent 不依赖 `print()`、`rich` 或具体界面，因此同一 Agent 可以复用于 REPL、单次命令和 Web 服务。

## 10. 工具调用被中断时如何修复对话历史

用户按 Ctrl+C 可能发生在工具调用已被写入 assistant 消息、但部分工具结果尚未写入历史的时刻。若直接结束，历史就违反“每个 tool call 必须有对应 tool result”的协议。

因此主循环捕获 `KeyboardInterrupt` 后，会调用 `_answer_pending_tool_calls()`：

```python
answered = {m.get("tool_call_id") for m in self.messages if m.get("role") == "tool"}
```

它先找出已有结果的 id，再仅为缺失的 id 追加：

```python
{
    "role": "tool",
    "tool_call_id": tc.id,
    "content": "[interrupted]",
}
```

补齐后才重新抛出 `KeyboardInterrupt` 给上层 CLI。这样用户下次继续对话时，历史仍然符合 API 协议；已完成的工具结果也不会被占位文本覆盖。

设计目的：清空历史会丢失已经完成的工作和上下文。补齐缺失结果只修复协议不变量，同时保留有价值的会话状态。

## 11. 上下文压缩如何接入主循环

`chat()` 在写入用户输入后、以及每轮工具执行结束后调用：

```python
self.context.maybe_compress(self.messages, self.llm)
```

工具输出往往比普通对话长，是上下文快速膨胀的主要来源。上下文管理器会在接近窗口限制时截短冗长输出、总结旧消息或进行强制压缩。这样下一轮发送给 LLM 的历史仍可放入上下文窗口。

`Agent` 只负责在合适的时机调用上下文管理器；具体的阈值、截断和摘要策略由 `ContextManager` 实现。将这部分拆出后，主循环保持“请求模型、执行工具、回填结果”的职责，压缩策略可以单独演进。

## 12. 会话历史清空如何设计

`reset()` 的实现保持很小：

```python
def reset(self):
    self.messages.clear()
```

它只清空对话历史，不替换 LLM、工具集、系统提示词或上下文配置。因此 `/reset` 之后仍使用同一个 Agent 配置，只是下一次 `chat()` 从空历史开始。

## 13. Agent 运行期不变量如何维护

以下不变量比“能调用工具”更能说明该实现的工程设计：

| 不变量                  | 代码中的做法                         | 避免的问题                           |
| ----------------------- | ------------------------------------ | ------------------------------------ |
| 循环有上限              | `max_rounds`                         | 模型或工具调用无限循环               |
| 每个工具调用都有结果    | `tool_call_id` 配对和中断补齐        | 后续 API 请求因历史不合法而失败      |
| 工具权限属于 Agent 实例 | `_tool_by_name` 从 `self.tools` 构建 | 受限或子 Agent 越权调用全局工具      |
| 参数错误与运行错误分开  | `signature(...).bind()` 后再执行     | 向模型反馈错误原因，导致错误修正方向 |
| 批处理结果顺序稳定      | 按 `futures` 原始顺序取 `result()`   | 工具结果与原始调用顺序混乱           |
| 表现层可替换            | `on_token` 与 `on_tool` 回调         | Agent 被终端实现绑定，难以复用       |

CoreCoder 与成熟 Agent 系统共享“模型决策、工具执行、结果回填、再次决策”的骨架。它的实现刻意较小；重试、上下文压缩和预算限制被拆到其他模块。介绍时应同时说明它的核心设计和当前边界，例如工具并发安全策略仍较简单。



# 工具系统的设计

本章对应教程 [02-tools_EN.md](../CoreCoder/article/02-tools_EN.md) 和 `corecoder/tools/`。介绍 CoreCoder 时，可以把工具概括为 Agent 接触外部世界的“手”：模型本身只生成文本；读取文件、修改文件、搜索代码、执行命令和委派子任务，都必须通过工具请求并由本地程序执行。

## 1. 工具系统的整体结构

一次工具调用大致经过以下路径：

```text
工具类定义 name / description / parameters / execute
-> Tool.schema() 转换为 function-calling schema
-> Agent 将当前允许的 schema 发送给模型
-> 模型返回工具名和参数
-> Agent 校验参数并执行 execute()
-> 工具返回文本结果
-> 结果作为 tool 消息回传给模型
```

`tools/base.py` 中的 `Tool` 是最小接口，所有工具直接继承它：

| 成员          | 作用                 | 介绍时的说法                                        |
| ------------- | -------------------- | --------------------------------------------------- |
| `name`        | 工具的稳定标识       | 模型用它指定要调用哪个工具。                        |
| `description` | 给模型阅读的能力说明 | 它决定模型知道工具能做什么、何时该用。              |
| `parameters`  | 参数的 JSON Schema   | 它约束模型应提供哪些字段及字段类型。                |
| `execute()`   | 本地实际执行逻辑     | 这里才拥有读写文件或运行命令的能力。                |
| `schema()`    | 协议适配             | 将前三项包装成 OpenAI function calling 所需的格式。 |

所有 `execute()` 都以字符串返回结果。这样成功信息、搜索结果、命令输出和可理解的错误信息，都能用同一种 `tool` 消息回传给模型。工具不是模型直接执行的函数；模型只能提出请求，Agent 才握有实际执行权。

工具不再继续拆成复杂的文件工具、搜索工具等继承层次，而是都直接继承 `Tool`。原因是它们真正共享的行为很少，保留一个小接口比为复用而复用的继承关系更容易理解和扩展。

小接口只规定每个工具都要有名称、说明、参数 schema 和 `execute()`。真正重复的路径解析等小功能可提取为普通辅助函数；不要为此让无关工具继承同一个父类。这样新增工具时只需实现这四项，不会因修改一个“通用父类”而影响其他工具。

**现有结构（本项目）**：
Tool
├── ReadFileTool
├── WriteFileTool
├── EditFileTool
├── GlobTool
├── GrepTool
├── BashTool
└── AgentTool

**继承结构**（容易把只适合某一子类的逻辑放入父类，过于复杂和耦合）：
Tool
├── FileTool
│   ├── ReadFileTool
│   ├── WriteFileTool
│   └── EditFileTool
└── SearchTool
    ├── GlobTool
    └── GrepTool

## 2. 工具注册与当前工具范围

`tools/__init__.py` 的 `ALL_TOOLS` 是全局注册表。当前注册了七个工具：

| 工具名       | 实现类          | 主要用途                            |
| ------------ | --------------- | ----------------------------------- |
| `bash`       | `BashTool`      | 运行 Shell 命令、测试、Git 操作等。 |
| `read_file`  | `ReadFileTool`  | 按行读取文本文件。                  |
| `write_file` | `WriteFileTool` | 创建文件或完整覆盖文件。            |
| `edit_file`  | `EditFileTool`  | 对唯一文本片段进行精确替换。        |
| `glob`       | `GlobTool`      | 按文件名模式查找文件。              |
| `grep`       | `GrepTool`      | 用正则表达式搜索文件内容。          |
| `agent`      | `AgentTool`     | 创建独立上下文的子 Agent。          |

将实例加入 `ALL_TOOLS` 后，默认 Agent 就能把它的 schema 提供给模型。实际执行时，Agent 仍从自己的 `self.tools` 建立名称索引，因此全局注册不等于每个 Agent 都有该权限；受限 Agent 可以只传入部分工具。

介绍时的常见问题：为什么模型不直接调用 Python 函数？模型运行在 API 服务端，本项目的 Python 代码运行在本地，两者只能交换结构化数据。模型返回的是按协议组织的“工具名 + 参数”，例如：

```json
{"name": "read_file", "arguments": {"file_path": "app.py", "limit": 100}}
```

本地 Agent 再根据工具名查找 `ReadFileTool`、校验参数，并调用 `execute()`。因此模型只能请求操作，不能自行执行本地代码；程序可以在执行前拒绝未知工具、错误参数或危险操作。

## 3. 读、写与编辑文件的分工

### 3.1 `read_file`：带行号的分页读取

`ReadFileTool` 先将路径扩展并解析为绝对路径，再区分“不存在”和“路径是目录”两种错误。读取时使用 UTF-8 和 `errors="replace"`，遇到不可解码的字节会以替代字符显示，而不会直接中断读取。

它将文本按行拆分，并根据 `offset` 和 `limit` 截取窗口：

```text
offset 是从 1 开始的首行号
limit 是最多返回的行数，默认 2000
输出格式：行号 + 制表符 + 原始行内容
```

若文件未完全展示，结果末尾会注明总行数和当前展示范围。行号的主要价值是帮助模型和用户定位和讨论代码；它不应被当作后续编辑的唯一依据，因为文件内容变化后行号会移动。

### 3.2 `write_file`：完整写入

`WriteFileTool` 用于新建文件或整体重写已有文件。它会先用 `mkdir(parents=True, exist_ok=True)` 创建缺失的父目录，然后以 UTF-8 写入完整 `content`，并将路径加入 `_changed_files` 集合，供会话中的 `/diff` 之类功能追踪。

它适合创建新文件或明确要整体替换的场景；对已有文件的小修改，工具描述明确建议使用 `edit_file`。原因是整份文件重写会让模型重复输出大量未改内容，成本更高，也更容易在复制过程中损坏无关部分。

### 3.3 `edit_file`：唯一匹配的搜索替换

`EditFileTool` 不使用“修改第 N 行”，也不要求模型生成标准 patch。模型提供三个参数：

```text
file_path   目标文件
old_string  文件中原有的完整文本片段
new_string  要替换成的新文本片段
```

核心约束是 `old_string` 必须在文件中恰好出现一次：

| 匹配次数  | 工具行为                       | 设计目的                           |
| --------- | ------------------------------ | ---------------------------------- |
| 0 次      | 返回错误和文件前 500 个字符    | 让模型重新读取或纠正记忆中的文本。 |
| 多于 1 次 | 拒绝执行，并要求加入更多上下文 | 避免猜测模型想修改哪一处。         |
| 1 次      | 只替换一次并写回文件           | 让编辑目标唯一、确定且可复核。     |

它使用严格的 UTF-8 解码；二进制文件或非 UTF-8 文件会得到简短错误，而不是把解码异常堆栈塞进模型上下文。替换本身先在内存中执行：`content.replace(old_string, new_string, 1)` 生成完整的新字符串；随后 `p.write_text(new_content, encoding="utf-8")` 根据文件路径从头覆盖写入整份新内容。`write_text()` 不需要知道旧文本的位置，位置已经体现在 `new_content` 的整体内容中。

写入成功后，工具用 `difflib.unified_diff` 根据旧内容和新内容生成统一 diff，并返回给模型和用户。这里的关键取舍是：让模型生成带行号的 diff 容易出错，而由程序生成 diff 是确定的；模型只需阅读和确认程序生成的结果。过长的 diff 会截断，避免占满上下文。

介绍时的常见问题：为什么不用行号编辑？模型容易记错或遇到文件变动后的偏移。为什么不用整份文件重写？大文件成本高且易误改。唯一文本替换用“引用真实代码片段”代替“猜测位置”，在可靠性、成本和实现复杂度之间更平衡。

## 4. 两种搜索工具如何配合

`glob` 解决“哪些文件可能相关”，`grep` 解决“这些文件中哪些行包含目标内容”。常见流程是先用 `glob` 找到候选文件，再用 `grep` 缩小到具体行，最后用 `read_file` 阅读必要上下文。

| 工具   | 匹配对象 | 关键行为                                         | 上限与取舍                              |
| ------ | -------- | ------------------------------------------------ | --------------------------------------- |
| `glob` | 文件路径 | 支持 `**` 递归匹配；按修改时间从新到旧排序。     | 最多展示 100 个结果，避免目录过大。     |
| `grep` | 文件内容 | 编译正则后逐行搜索，返回文件路径、行号和匹配行。 | 最多遍历 5000 个文件、返回 200 个匹配。 |

`glob` 要求搜索根路径是目录，未匹配时返回 `No files matched.`。`grep` 的 `include` 参数可进一步限制文件名模式，例如 `*.py`；传入的正则无法编译时，它返回 `Invalid regex`，而不是让工具崩溃。

`grep` 会跳过 `.git`、`node_modules`、虚拟环境、构建产物等噪声目录。实现时只检查“搜索根目录以内”的相对路径部分，避免搜索根目录的上级目录恰好叫 `build` 时误把整棵树排除。读取搜索文件时使用 `errors="ignore"`，对无法读取的文件则跳过，这使大规模代码搜索更稳健，但也意味着它并非二进制内容搜索工具。

## 5. `bash`：实用的防误操作，不是沙箱

`BashTool` 通过 `subprocess.run(..., shell=True)` 执行命令，捕获标准输出和标准错误，并在非零退出码时把退出码附在结果中。一次 `BashTool.execute()` 调用只启动一个临时 Shell；`command` 字符串中的 `&&` 等多条命令会在该 Shell 内顺序执行。调用结束后，这个 Shell 会退出.

它还提供三个面向 Agent 使用场景的保护：

| 机制         | 代码行为                                        | 解决的问题                                             |
| ------------ | ----------------------------------------------- | ------------------------------------------------------ |
| 超时         | `timeout` 默认 120 秒；超时返回错误文本。       | 避免命令无限等待。                                     |
| 输出截断     | 超过 15000 字符时保留前 6000 和后 3000 字符。   | 避免海量输出挤占模型上下文，同时保留开头和结尾信息。   |
| 工作目录跟踪 | 仅当命令成功后解析 `cd`；每个线程各自保存 cwd。 | 使连续命令能沿用目录，又避免并发线程争用一个全局 cwd。 |

### 临时 Shell 的工作目录状态管理
>Agent调用多个工具会通过ThreadPoolExecutor创建线程并发执行工具。每个线程都有自己的工作目录状态，避免不同线程的命令争用同一个目录。
但调用一个工具时当前 Agent 线程执行不调用新线程。

**为使多次工具调用具有连续终端的工作目录体验**，工具维护一个虚拟工作目录，而不是调用 `os.chdir()` 修改 Python 进程的全局工作目录。`_local` 是 `threading.local()` 创建的线程本地存储对象；`_local.cwd` 保存当前线程下一次 Bash 调用应使用的目录。不同线程的 `_local.cwd` 相互独立，避免并发命令争用同一个目录状态。

每次执行时，代码优先读取 `_local.cwd`，没有记录时才使用 `os.getcwd()`，并通过 `subprocess.run(..., cwd=cwd)` 将该目录传给临时 Shell。命令成功后才调用 `_update_cwd(command, cwd)`；命令失败时保留原有虚拟工作目录。这样目录状态只影响后续 Bash 子进程，不影响宿主 Python 进程或其他线程。

`_update_cwd()` 使用 `running` 保存解析过程中的目录，并按 `&&` 分割命令。它只处理以 `cd ` 开头的片段：提取目标路径、展开 `~`、相对 `running` 拼接路径、规范化路径，并在目标确实是目录时更新 `running`。全部处理结束后，若目录发生变化，就写入 `_local.cwd`。

例如初始目录为 `/project`，成功执行 `cd a && cd b` 时，解析过程为：

```text
/project
-> cd a
-> /project/a
-> cd b
-> /project/a/b
```

下一次 Bash 调用会以 `/project/a/b` 为 `cwd` 启动临时 Shell。因此，单次调用内由 Shell 自己处理目录变化，多次调用之间由 `_local.cwd` 模拟目录延续。

该实现是轻量级状态同步，而不是完整的 Shell 解析器。它不能可靠处理引号中的 `&&`、变量展开、`;`、`pushd`、子 Shell 等复杂写法；对这些场景，需要持久 Shell 会话或完整的 Shell 解析方案。

执行前，`_check_dangerous()` 依次用正则检查危险模式，例如：递归删除根目录或家目录、递归加强制删除、格式化文件系统、向原始磁盘设备写入、根目录上的危险权限修改、fork bomb，以及把 `curl` 或 `wget` 直接管道给 Shell。命中后不会执行命令，而是返回 `Blocked` 和原因。

`rm` 规则体现了“识别变体而不误拦截”的原则：`rm -rf`、`rm -fr`、`rm -r -f`、`rm -f -r` 都是递归加强制删除，规则会识别它们及 `--recursive --force` 的长选项；而 `rm -f notes.log` 仅删除单个文件，`rm -r ./build_output` 常用于删除当前项目的构建输出目录，两者不应被这条组合规则一概拦截。后者仍有删除风险，所谓“允许”只表示它不符合此处的高风险启发式规则。

最重要的边界是：正则黑名单不是安全边界。命令可以借助编码、变量拼接或其他 Shell 形式绕过检查，且 `shell=True` 本身允许复杂命令解释。它适合防止模型意外生成最直白的灾难命令，不足以对抗恶意输入或不可信环境。若要用于真实隔离场景，应增加操作系统级沙箱、最小权限运行账户、目录白名单、资源限制和明确的人工审批。

## 6. `agent`：用隔离上下文委派子任务

`AgentTool` 让主 Agent 把复杂子任务交给新的 `Agent` 实例。它依赖 `Agent.__init__()` 注入的 `_parent_agent`，从父 Agent 继承 LLM、最大上下文大小和当前工具范围；创建子 Agent 时会移除 `agent` 工具本身，以避免无限递归地创建子 Agent。

子 Agent 拥有自己的消息历史，最多运行 20 轮，结束后只把文本总结返回给父 Agent。结果超过 5000 个字符会截断为前 4500 个字符并加提示，避免子任务报告反过来撑满父 Agent 的上下文。

它解决的不是并行计算本身，而是上下文隔离：例如让子 Agent 独立研究代码库、完成局部实现，再把结论交给主 Agent。其边界是它仍与父 Agent 处于同一进程和权限模型中，不是安全隔离；工具范围继承也意味着父 Agent 给出的权限必须足够谨慎。

## 7. 两阶段校验与错误信息设计

工具调用有两道不同的门：

```text
第一阶段：Agent 用 execute() 的函数签名校验参数形状
第二阶段：工具根据业务和安全规则决定是否执行
```

CoreCoder 对一次工具调用其实做了两道关。第一道在 `agent._exec_tool` 里，用 `inspect.signature().bind()` 验参数能不能对上函数签名，这是验「形状」。第二道在工具内部，比如 `bash` 的危险命令检测、`edit_file` 的 UTF-8 判断，这是验「该不该真做」。

工具中的错误文本同样是协议的一部分。`old_string not found` 会附带文件开头以帮助模型纠正内容；`old_string appears N times` 明确要求更多上下文；`Invalid regex` 和文件不存在也直接说明原因。对模型而言，清晰的错误是下一轮行动的输入，而不是仅供开发者阅读的异常日志。

## 8. 如何新增一个工具

新增工具的最小步骤：

1. 在 `corecoder/tools/` 创建一个直接继承 `Tool` 的类。
2. 写清 `name`、面向模型的 `description` 和 JSON Schema `parameters`。
3. 实现 `execute()`，将成功和可恢复错误转换为简洁字符串。
4. 在 `tools/__init__.py` 导入类，并将实例加入 `ALL_TOOLS`。
5. 在 `tests/test_tools.py` 增加 schema 与关键行为测试。

`description` 不能只写一个模糊名词，应同时说明工具的能力、何时使用及主要限制，因为它是模型选择工具的重要依据。参数 schema 要与 `execute()` 的函数签名保持一致；否则模型看见的接口和本地校验的接口会互相矛盾。

一个无参数工具的 schema 可以写成：

```python
parameters = {
    "type": "object",
    "properties": {},
    "required": [],
}
```

## 9. 测试如何证明工具设计有效

`tests/test_tools.py` 不只验证“代码能运行”，还验证工具设计的边界：

| 测试类别            | 覆盖的设计点                                                               |
| ------------------- | -------------------------------------------------------------------------- |
| 所有工具 schema     | 每个注册工具都能生成合法的 function-calling 描述。                         |
| Bash 危险命令变体   | 递归强制删除、长选项、fork bomb 和下载后直接执行会被拦截。                 |
| Bash 正常命令与 cwd | 正常 `rm` 不误拦截；链式 `cd` 按顺序解析；线程 cwd 互不干扰。              |
| 文件读写            | UTF-8 内容可往返、读取窗口正确、写入能创建父目录。                         |
| 精确编辑            | 唯一替换会写入并返回 diff；找不到、重复文本和非 UTF-8 文件会得到可读错误。 |
| 搜索工具            | 无结果、非法正则、无效路径和跳过噪声目录都有确定行为。                     |

介绍项目时，可以将这些测试作为设计证据：工具的价值不只是“提供能力”，还包括明确地说明哪些请求应成功、哪些应失败、失败时模型会得到什么反馈。

# LLM 接入、流式响应处理与成本统计

本章对应 `corecoder/llm.py` 和文章 `03-llm-and-cost_EN.md`。该层位于 Agent 与模型服务之间，负责组装 OpenAI 兼容请求、处理流式响应、将工具调用碎片还原为统一响应，并记录 Token 与估算成本。Agent 只接收完整的 `LLMResponse`，不处理 provider 的流式数据或重试细节。

## 1. LLM 接入的整体处理路径

`llm.py` 的接入层将配置、不同 provider 后端和流式响应处理收敛为统一路径：

```text
Config / CLI 提供 model、api_key、base_url、provider 和额外参数
-> 根据 provider 创建 LLM 或 LiteLLM
   -> LLM：创建 OpenAI SDK 客户端
   -> LiteLLM：保存 API Key 和地址，由 LiteLLM 路由请求
-> chat() 组装 model / messages / tools / stream 请求
-> _call_with_retry() 调用对应 SDK，并处理瞬时故障重试
-> SDK 返回流式 chunk
   -> 累积文本增量
   -> 按工具调用 index 累积参数碎片并解析 JSON
   -> 读取末尾 usage 并累计 Token
-> 返回统一的 LLMResponse
-> 根据累计 Token 与 _PRICING 计算 estimated_cost
```

该层将 provider 协议、网络重试、流式解析、Token 统计和成本估算封装在 `LLM` / `LiteLLM` 中。上层只需传入消息和工具 schema，并消费统一的 `LLMResponse`。

## 2. LLM 响应与 Agent 如何衔接

`LLMResponse` 是 provider 层交给 Agent 的统一结果：

```python
@dataclass
class LLMResponse:
    content: str = ""
    tool_calls: list[ToolCall] = field(default_factory=list)
    prompt_tokens: int = 0
    completion_tokens: int = 0
```

`content` 保存完整文本，`tool_calls` 保存已经解析的工具调用，两个 Token 字段记录当前一次模型请求的用量。`Agent.chat()` 根据 `tool_calls` 是否为空决定结束本轮还是执行工具，因此 Agent 不需要知道文本和工具参数曾经以多少个流式块到达。

`LLMResponse.message` 会将结果转换为 OpenAI 兼容的 assistant 消息。工具参数在保存历史前重新序列化为 JSON 字符串；Agent 随后追加带相同 `tool_call_id` 的 tool 消息。这样 provider 层输出、Agent 工具执行和下一轮模型请求共享同一套消息协议。

## 3. Provider 接入如何分层

**本项目有两种接入层实现**：
- **LLM**：直接使用 OpenAI SDK，适用于 OpenAI 兼容接口。更换 DeepSeek、Qwen、Ollama 等通常只需改变 base_url、API Key 和模型名。
- **LiteLLM**：使用 LiteLLM 路由，适用于不直接兼容 OpenAI 接口的 provider。

主路径使用 `LLM`：

```python
self.client = OpenAI(api_key=api_key, base_url=base_url)
```

它假定目标服务暴露 OpenAI 兼容接口。模型名、API Key 和 `base_url` 都由配置传入，因此切换兼容 provider 不需要改 Agent 或工具代码。

`LiteLLM` 继承 `LLM` 的统一响应格式和成本统计方式，但不创建 OpenAI 客户端，而是把请求交给 `litellm.completion(...)`。它用于不直接提供 OpenAI 兼容接口的 provider。CLI 根据 `CORECODER_PROVIDER` 选择创建 `LLM` 或 `LiteLLM`，上层 Agent 不依赖具体后端类型。

## 4. 一次模型请求如何构造与降级

`LLM.chat()` 接收 Agent 提供的消息历史、工具 schema 和可选的 `on_token` 回调，并构造请求参数：

```python
params = {
    "model": self.model,
    "messages": messages,
    "stream": True,
    **self.extra,
}
```

`self.extra` 保存初始化时传入的温度、最大输出 Token 等额外参数。只有当前 Agent 有工具时才加入 `tools` 字段，因此模型看到的是该 Agent 当前允许调用的工具范围，而不是全局任意工具。

请求始终设置 `stream=True`，使 SDK 返回可迭代的响应流，而不是一次性完整响应。代码还会尝试加入：

```python
params["stream_options"] = {"include_usage": True}
```

该参数用于请求流末尾的 Token 用量。部分 OpenAI 兼容 provider 会拒绝它；收到 `BadRequestError` 后，代码删除 `stream_options` 并重新发起一次请求。参数兼容性降级放在 `chat()`，瞬时故障重试放在 `_call_with_retry()`，两类失败原因和重试边界保持分离。

## 5. 流式文本如何累积并实时显示

SDK 在 `for chunk in stream` 中逐块返回响应。流式对象的层级和含义如下：

```text
stream
-> chunk：服务端在当前时刻发送的一块增量数据，不等于完整回答
   -> choices：当前块中候选回答的列表
      -> choice.delta：该候选回答相对前面块新增的内容
```

一个 `chunk` 可以只包含文本增量、工具调用增量或末尾的用量信息；服务端决定块的边界。

**`chiices`中的候选回答就是类似于`chatgpt`，`deepseek`等模型回答时的不同版本的回答**，`choices` 中的每个元素代表同一输入下的一份独立候选回答，不是文本分块。当前项目默认请求单候选，并且只读取列表中的第一个候选；它不实现多个候选回答的独立累积、比较或选择。：
```txt
一次请求
├── 候选回答 0
│   ├── chunk 1：delta.content = "你好"
│   ├── chunk 2：delta.content = "，我是"
│   └── chunk 3：delta.content = " CoreCoder。"
└── 候选回答 1（仅在请求多个候选时才有）
    ├── chunk 1：delta.content = "您好"
    └── chunk 2：delta.content = "，有什么可以帮您？"
```

`delta` 是增量对象，可能携带 `content`、`tool_calls` 或其他本次新到达的字段，而不是整次模型回复。用量块可能没有 `choices`，因此代码先记录 `usage`，再跳过没有候选输出的块：

```python
if not chunk.choices:
    continue
delta = chunk.choices[0].delta
```

空 `choices` 表示当前块没有候选输出，`continue` 会跳过该块。`chunk.choices[0]` 选择第一个候选；若调用方显式请求多个候选，其他候选的文本和工具调用不会进入当前 `LLMResponse`。

文本增量通过列表累积：

```python
if delta.content:
    content_parts.append(delta.content)
    if on_token:
        on_token(delta.content)
```

流结束后，`"".join(content_parts)` 生成完整文本。`on_token` 在每段文本到达时触发并返回当前内容到客户端以**达到客户端的流式输出**，由 CLI 或其他界面决定如何显示；provider 层不依赖终端输出实现。

## 6. 流式工具调用如何还原

`delta.tool_calls` 表示当前流式块包含模型提出的工具调用增量。它是 LLM 发给 Agent 的执行请求，不是工具执行结果。工具结果由 Agent 生成并在下一轮作为 `role="tool"` 消息发送回模型。

一个 `chunk` 可以包含完整工具调用，也可以只包含部分字段。完整调用到达时，`id`、工具名和参数只会各处理一次；参数碎片化到达时，`id` 与工具名通常先出现，后续块继续提供参数字符串。多个工具调用的碎片也可能交错出现。

`tc_delta.index` 表示该调用在当前 assistant 响应中的顺序，不是 chunk 序号，也不是候选回答序号。它也不同于 `chunk.choices[0]`：后者选择第一个候选回答，前者标识该候选回答中的第几个工具调用。代码使用工具调用序号作为累积键：
```text
chunk 1 → 工具 0：arguments = '{"path":"a'
chunk 2 → 工具 1：arguments = '{"path":"b'
chunk 3 → 工具 0：arguments = '.py"}'
chunk 4 → 工具 1：arguments = '.py"}'
```

```python
tc_map: dict[int, dict] = {}

for tc_delta in delta.tool_calls:
    idx = tc_delta.index
    if idx not in tc_map:
        tc_map[idx] = {"id": "", "name": "", "args": ""}
```

`id` 和工具名保存最后一个非空值，不进行字符串拼接；参数字符串才按到达顺序使用 `+=` 拼接。因此，无论参数一次完整到达还是分多次到达，都会形成同一个 `args` 字符串：

```python
if tc_delta.function.arguments:
    tc_map[idx]["args"] += tc_delta.function.arguments
```

流结束后，代码按 `index` 排序，使用 `json.loads()` 将每个完整参数字符串转换为字典，并生成 `ToolCall`。若参数缺失或不是合法 JSON，则使用空字典而不是中断整个响应处理；后续的 Agent 参数校验会将不匹配的调用转换为可返回给模型的错误信息。

## 7. Token 用量与成本如何统计

启用 `include_usage` 后，provider 可在流的末尾返回 `usage`。代码读取当前请求的输入和输出 Token：

```python
prompt_tok = chunk.usage.prompt_tokens or 0
completion_tok = chunk.usage.completion_tokens or 0
```

`or 0` 处理 provider 返回 `null` 用量字段的情况，避免累计时出现 `int + None`。

当前请求结束后，数值累加到 `total_prompt_tokens` 和 `total_completion_tokens`，供会话中的 `/tokens` 命令读取。
```python
self.total_prompt_tokens += prompt_tok
self.total_completion_tokens += completion_tok
```
`_PRICING` 保存每百万 Token 的输入与输出单价：

```python
"gpt-5.5": (5, 30)
```

`estimated_cost` 用累计 Token 乘以对应费率，返回美元估算值。模型不在价格表中时返回 `None`，不会编造价格。该成本只基于项目维护的静态输入、输出单价和 provider 返回的用量；代码没有实现按美元强制停止、缓存折扣或批处理定价计算。

## 8. 瞬时故障与服务端错误如何重试

`_call_with_retry()` 负责 provider 调用的瞬时故障重试，Agent 主循环不包含重试逻辑。默认最多尝试三次：第一次和第二次失败后分别等待 1 秒、2 秒；第三次仍失败时抛出原始异常。

```python
wait = 2 ** attempt
time.sleep(wait)
```

限流、超时和连接错误会重试。其他 `APIError` 仅在 `status_code >= 500` 时重试；4xx 请求错误直接抛出，因为原样重试不会修复参数、鉴权或权限问题。读取 `status_code` 时使用 `getattr(e, "status_code", None)`，使缺少该属性的基础异常仍能被安全处理。

将重试放在 provider 层可以使 Agent 循环只维护“模型决策、工具执行、结果回填”的状态机，并使所有使用同一 `LLM` 实例的调用共享一致的网络故障策略。

## 9. LiteLLM 的兼容性处理

LiteLLM 后端在请求中加入：

```python
params["drop_params"] = True
```

不支持某个参数的 provider 会由 LiteLLM 丢弃该参数，而不是直接报错。API Key 与自定义地址分别映射为 `api_key` 和 `api_base`。

不同 provider 的流式对象可能缺少部分属性，因此 LiteLLM 读取字段时使用：

```python
usage = getattr(chunk, "usage", None)
```

这表示属性存在时读取其值，属性不存在时返回 `None`，避免抛出 `AttributeError`。主 `LLM` 依赖 OpenAI SDK 的固定响应结构，直接使用 `chunk.usage`、`chunk.choices` 等属性；LiteLLM 则以同一套累积逻辑适配更宽松的对象形状。

两种写法处理的风险不同：

```python
if chunk.usage:
    ...
```

主 `LLM`使用的是OpenAI协议,假定 `usage` 属性一定存在；它只处理属性值为 `None` 或为空的情况。若属性本身缺失，访问 `chunk.usage` 会抛出 `AttributeError`。

```python
usage = getattr(chunk, "usage", None)
if usage:
    ...
```

`getattr(chunk, "usage", None)` 的效果近似于“有 `usage` 属性就读取，没有就使用 `None`”。LiteLLM 对 `usage`、`choices`、`content` 和 `tool_calls` 都采用这一防御式读取方式，因为不同 provider 或 LiteLLM 版本的流式对象不一定具备完全相同的属性。`getattr` 只处理属性缺失，不验证属性值的类型或内容。

## 10. Provider 层的运行期不变量与边界

| 约束或边界                  | 代码中的做法                                      | 作用或影响                                   |
| --------------------------- | ------------------------------------------------- | -------------------------------------------- |
| 上层只接收完整响应          | 返回 `LLMResponse`                                | Agent 不依赖 chunk、SDK 类型或 provider 差异 |
| 文本片段保持到达顺序        | `content_parts.append()` 后统一 `join()`          | 流式显示与最终文本一致                       |
| 工具调用顺序稳定            | 按 `tc_delta.index` 分组，结束后 `sorted(tc_map)` | 多个调用的参数碎片不会混合                   |
| 异常工具参数不使流解析失败  | 非法 JSON 降级为 `{}`                             | 参数问题交由 Agent 返回可理解的反馈          |
| 网络故障不进入 Agent 状态机 | provider 层指数退避重试                           | 避免主循环混入 HTTP 重试细节                 |
| 当前只支持单候选结果        | 只读取 `chunk.choices[0]`                         | 未实现多候选累积、选择或投票                 |
| 成本为估算而非硬限制        | `_PRICING` 与累计 Token                           | 未实现 fallback 模型和美元预算上限           |

# 上下文压缩与消息历史维护

本章对应 `corecoder/context.py` 和文章 `04-context.md`。`ContextManager` 负责在对话历史接近模型上下文上限时压缩消息；它接收并原地修改 `Agent.messages`，不负责模型请求、工具执行或会话持久化。

`messages` 是同一 `Agent` 实例的多轮对话历史，元素为符合 OpenAI 兼容协议的消息字典。`self.messages` 不包含 system message；`Agent._full_messages()` 会在每次请求模型前临时将 system message 放在第一个元素。上下文压缩处理的是 `self.messages`。

## 1. 上下文压缩的整体处理路径

上下文管理器在发送模型请求前和每轮工具执行后检查历史规模，并按从轻到重的策略修改同一个 `messages` 列表：

```text
Agent.chat()
-> 追加 user 消息，或追加 assistant 工具调用与 tool 结果
-> ContextManager.maybe_compress(messages, llm)
   -> estimate_tokens() 粗略估算 content 与 tool_calls 的 Token
   -> 超过 50%：_snip_tool_outputs()
      -> 截断过长的 tool content，保留前三行和后三行
      -> 重新估算 Token
   -> 超过 70% 且消息数大于 10：_summarize_old()
      -> _safe_split() 确定不拆开工具调用的边界
      -> _get_summary() 生成旧消息摘要
      -> 重建为摘要消息加近期 tail
      -> 重新估算 Token
   -> 超过 90% 且消息数大于 4：_hard_collapse()
      -> _safe_split() 确定安全边界
      -> 重建为硬折叠摘要加近期 tail
-> Agent._full_messages() 临时前置 system message
-> LLM.chat() 使用压缩后的完整历史发起请求
```

三层策略的共同目标是让历史保持可发送，同时优先保留近期原始消息和工具调用协议的完整性。`maybe_compress()` 返回是否发生过压缩；它通过原地修改 `messages` 影响同一轮及后续轮次的模型请求。

## 2. 消息历史与工具调用配对

消息字典按 `role` 使用不同字段组合：

| 消息类型 | 主要字段 | 用途 |
| --- | --- | --- |
| 用户消息 | `role: "user"`、`content` | 保存用户输入或压缩后的摘要。 |
| 普通模型回复 | `role: "assistant"`、`content` | 保存模型的文本回复。 |
| 工具调用请求 | `role: "assistant"`、`tool_calls` | 保存模型请求执行的一个或多个工具调用。 |
| 工具结果 | `role: "tool"`、`tool_call_id`、`content` | 保存工具执行结果。 |

工具结果中的 `tool_call_id` 必须对应前面 assistant 消息的 `tool_calls` 中的调用 ID。一个 assistant 消息可以包含多个工具调用，随后会有连续的多条 tool 消息。该配对关系是后续模型请求的协议不变量；压缩消息历史时不能将 tool 结果与生成它的 `tool_calls` 分开。

```text
self.messages 的局部结构

messages[i]     = {role: "assistant", tool_calls: [{id: "call_1"}, {id: "call_2"}]}
messages[i + 1] = {role: "tool", tool_call_id: "call_1", content: "..."}
messages[i + 2] = {role: "tool", tool_call_id: "call_2", content: "..."}
```

## 3. 压缩调度与 Token 估算

`maybe_compress()` 在一次调用中按从轻到重的顺序执行三层策略。第一层或第二层实际修改历史后，会重新估算 Token，再决定是否需要下一层；第三层是最后手段。

```text
estimate_tokens(messages)
-> 超过 50%：截断过长 tool 输出
-> 重新估算
-> 超过 70%：摘要旧消息并保留近期消息
-> 重新估算
-> 超过 90%：硬折叠为摘要加近期消息
```

| 阈值 | 触发条件 | 动作 |
| --- | --- | --- |
| 50% | `current > max_tokens * 0.50` | `_snip_tool_outputs()` 截断长工具结果。 |
| 70% | `current > max_tokens * 0.70` 且消息数大于 10 | `_summarize_old(..., keep_recent=8)`。 |
| 90% | `current > max_tokens * 0.90` 且消息数大于 4 | `_hard_collapse()`。 |

`estimate_tokens()` 只估算每条消息的 `content`，以及存在时的 `tool_calls` 的字符串表示。`_approx_tokens()` 使用 `len(text) // 3`，即按约三个字符一个 Token 估算中英文混合内容。该估算不使用模型的真实 tokenizer，因此仅用于判断压缩时机；中文、代码、符号密集文本的实际 Token 数可能与估算值有偏差。

Agent 在写入一条新的 user 消息后、以及每轮工具执行完成后调用 `maybe_compress()`。这样既能在请求模型前限制历史规模，也能在工具输出膨胀后及时压缩。

## 4. 第一层：截断过长的工具结果

`_snip_tool_outputs()` 只处理 `role == "tool"` 的消息。工具输出通常包含日志、命令结果或搜索结果，体积大且大部分内容在后续轮次中价值较低；用户要求、模型决策和普通 assistant 回复不在这一层直接截断。

一条 tool 消息满足以下条件时会被替换：

```text
content 字符数大于 1500
并且按行拆分后的行数大于 6
```

替换后的内容保留前三行、截断提示和后三行：

```text
原 tool content
第一行
第二行
第三行
... 中间大量内容 ...
倒数第三行
倒数第二行
最后一行

压缩后
第一行
第二行
第三行
... (N lines, snipped to save context) ...
倒数第三行
倒数第二行
最后一行
```

首部通常描述命令或操作，尾部常包含结果或报错；保留两端可以在减少 Token 的同时留下基本线索。该实现按当前历史中的所有 tool 消息扫描，不区分消息新旧。单行但超过 1500 个字符的输出不会被这一层截断，因为行数不大于 6。

## 5. 第二层：摘要旧消息

`_summarize_old()` 默认保留最近 8 条消息，并将安全切分点之前的旧消息替换为摘要。其重建结果为：

```text
压缩前
[old 消息 ...] [安全切分点] [tail：近期原始消息 ...]

压缩后
[
  {role: "user", content: "[Context compressed - conversation summary]\\n..."},
  {role: "assistant", content: "Got it, I have the context from our earlier conversation."},
  tail 中的原始消息...
]
```

`old = messages[:split]` 和 `tail = messages[split:]` 创建两个列表切片。完成摘要后，代码使用 `messages.clear()` 清空原列表，再通过 `append()` 加入两条摘要消息，并用 `extend(tail)` 将 tail 中的每个原始消息字典依次接回。该过程保留的是同一个 `messages` 列表对象，因此持有该列表引用的调用方会看到压缩后的内容。

### 5.1 LLM 摘要的输入边界

`_get_summary()` 先调用 `_flatten()` 将待摘要消息转为文本。`_flatten()` 只读取每条消息的 `role` 和 `content`，并将每条非空内容限制为前 400 个字符：

```text
[user] 前 400 个字符
[tool] 前 400 个字符
[assistant] 前 400 个字符
```

随后，调用 LLM 时只传入 `flat[:15000]`，即最多 15,000 个字符的扁平文本。摘要 system 指令要求保留文件路径、关键决策、已遇到的错误和当前任务状态，并丢弃冗长命令输出、代码清单和重复对话。

该路径是有损压缩。每条内容第 400 个字符之后的文本、扁平文本第 15,000 个字符之后的内容，以及 `tool_calls` 和 `tool_call_id` 字段都不会进入 LLM 摘要。LLM 还会基于输入生成更短的摘要。近期 tail 保持原始消息，降低当前任务状态被丢失的风险，但已被摘要替换的细节无法恢复。

### 5.2 无 LLM 或摘要失败时的降级

当 `llm` 为 `None`，或 `llm.chat()` 抛出异常时，`_get_summary()` 调用 `_extract_key_info(messages)`。该分支扫描原始消息的 `content`，不经过每条 400 字符和总计 15,000 字符的 LLM 输入限制，但只提取两类启发式信息：

| 提取目标 | 当前实现 | 输出限制与边界 |
| --- | --- | --- |
| 文件路径 | 正则 `r'[\\w./\\-]+\\.\\w{1,5}'` 扫描文本；结果加入 `set` 去重。 | 按字符串字典序排序后最多保留 20 项；不访问文件系统，也不验证路径存在。对 Windows 完整反斜杠路径的识别不完整。 |
| 错误行 | 按行拆分，若 `"error" in line.lower()` 则记录。 | 每行去除首尾空白后最多 150 个字符，最多保留 5 行；不能识别只包含“错误”或 `exception` 的行，也可能记录普通说明中的 `error`。 |

若两类信息都没有，返回 `"(no extractable context)"`。当前降级实现不会从文本中提取关键决策；`_extract_key_info()` 的 docstring 中提到 decisions，但其实际代码只输出文件路径和错误行。

## 6. 安全切分：避免孤儿 tool 消息

`_safe_split()` 用于第二层和第三层压缩。它先计算“保留最近 N 条”的初始切分点，再在切分点恰好指向 tool 消息时持续向前移动：

```python
split = max(0, len(messages) - keep_recent)
while split > 0 and messages[split].get("role") == "tool":
    split -= 1
return split
```

该实现不直接读取 `tool_call_id`，而是依赖 Agent 已按协议写入历史的顺序：带 `tool_calls` 的 assistant 消息后紧跟其一个或多个 tool 结果。遇到连续 tool 消息时，循环会越过整段 tool 结果，停在对应 assistant 消息的位置，使 tail 从该 assistant 消息开始。

### 6.1 错误切分结构

以下示例使用第三层压缩的实际保留数量。假设当前 `self.messages` 有 6 条消息，硬折叠的初始切分点是 `6 - 4 = 2`。若直接使用该切分点、不调用 `_safe_split()`，会拆开一次工具调用：

```text
压缩前 self.messages

索引          0                  1                         2                 3        4          5
           ┌──────────┐   ┌──────────────────────┐   ┌──────────────┐  ┌──────┐ ┌──────────┐ ┌──────┐
消息       │ user     │   │ assistant            │   │ tool         │  │ user │ │ assistant│ │ user │
           │          │   │ tool_calls: call_1   │   │ call_1       │  │      │ │ content  │ │      │
           └──────────┘   └──────────────────────┘   └──────────────┘  └──────┘ └──────────┘ └──────┘

old = messages[:2]                                   │ tail = messages[2:]
                                                       ↑ 初始切分点，指向 tool
```

`messages[1]` 会进入旧消息摘要，`messages[2]` 却留在 tail 中。重建历史后，结构会变成：

```text
[
  摘要 user 消息,
  摘要确认 assistant 消息，
  原 messages[2]：tool(tool_call_id = "call_1"),
  原 messages[3]，原 messages[4]，原 messages[5]
]
```

此时 tool 消息前面是摘要确认消息，而不是包含 `tool_calls: call_1` 的 assistant 消息；该 tool 结果失去来源，成为孤儿消息。将这段历史发送给 OpenAI 兼容 API 会违反工具调用配对约束。

### 6.2 安全切分结构

相同历史经过 `_safe_split(messages, 4)` 后，`messages[2]` 的角色为 `tool`，因此 `split` 从 `2` 回退到 `1`；`messages[1]` 是 assistant，循环停止。

```text
压缩前 self.messages

索引          0                 1                         2                 3        4          5
           ┌──────────┐  ┌──────────────────────┐   ┌──────────────┐  ┌──────┐ ┌──────────┐ ┌──────┐
消息       │ user     │  │ assistant            │   │ tool         │  │ user │ │ assistant│ │ user │
           │          │  │ tool_calls: call_1   │   │ call_1       │  │      │ │ content  │ │      │
           └──────────┘  └──────────────────────┘   └──────────────┘  └──────┘ └──────────┘ └──────┘

old = messages[:1]                     │ tail = messages[1:]
                                         ↑ 安全切分点，位于 assistant 之前
```

重建后的历史保留完整配对：

```text
[
  摘要 user 消息,
  摘要确认 assistant 消息,
  原 messages[1]：assistant(tool_calls: call_1),
  原 messages[2]：tool(tool_call_id: call_1),
  原 messages[3]，原 messages[4]，原 messages[5]
]
```

安全切分可能使保留的消息数超过目标值。示例原本计划保留最近 4 条，实际保留了 `messages[1:]` 的 5 条；协议正确性优先于严格的条数限制。

## 7. 第三层：硬折叠

`_hard_collapse()` 在估算 Token 超过 90% 且消息数大于 4 时执行。它同样使用 `_safe_split()`，但目标是只保留最近 4 条消息和摘要：

```text
[旧消息 ...] [安全切分点] [近期 tail ...]
->
[
  {role: "user", content: "[Hard context reset]\\n摘要"},
  {role: "assistant", content: "Context restored. Continuing from where we left off."},
  近期 tail ...
]
```

`_hard_collapse()` 通过原地清空和重建列表生效，且没有显式返回值。函数中的条件表达式为 `4 if len(messages) > 4 else 2`；当前正常调用点已要求消息数大于 4，因此实际传给 `_safe_split()` 的保留数量为 4。安全切分仍可能扩大最终 tail。

## 8. 设计边界与测试约束

| 设计点 | 当前实现的约束或影响 |
| --- | --- |
| 压缩是有损的 | 工具输出截断、每条 400 字符、总计 15,000 字符和 LLM 摘要都会删除信息。该设计以保留近期原始消息和摘要提示来降低影响，不能保证保留所有历史细节。 |
| Token 估算是近似值 | 字符数除以 3 不等同于模型 tokenizer；阈值只是触发压缩的近似依据。 |
| 工具协议优先于条数目标 | `_safe_split()` 可多保留一组 assistant/tool 消息，避免 API 因孤儿 tool 消息拒绝请求。 |
| 安全切分依赖输入历史已合法 | `_safe_split()` 只检查切分点是否为 `tool`，不验证 `tool_call_id` 是否真的对应前面的 `tool_calls`。Agent 正常写入顺序和测试共同维护该前提。 |
| LLM 摘要调用失败可继续运行 | 捕获异常后降级为正则和关键字提取；当前代码不记录该异常，也不会保留完整语义。 |

`tests/test_core.py` 固化了两项与工具消息相关的约束：

- `test_safe_split_never_orphans_a_tool_message` 验证安全切分后，保留尾部的首条消息不是 `tool`。
- `test_compress_never_leaves_an_orphan_tool_reply` 在压缩后遍历每条 tool 消息，验证其前一条消息仍是 tool，或带有 `tool_calls`。该测试验证相邻消息结构，不逐一校验 `tool_call_id` 与具体调用 ID 的精确对应关系。
