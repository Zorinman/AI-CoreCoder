# Problem Statement

Agent 在同一轮收到多个 tool_calls 时，只要数量大于 1 就统一丢进
`ThreadPoolExecutor` 并发执行，不区分工具是否具备并发安全性。多数内置工具
（`bash`、`edit_file`、`write_file`）会产生跨调用共享的副作用（进程 cwd、
磁盘文件内容），并发执行时可能出现结果相互覆盖、顺序错乱、或调试时无法复现
的竞态问题。当前唯一的隔离手段是 `bash` 工具用 `threading.local()` 隔离
每线程的 cwd，这只解决了 `bash` 自身的问题，没有解决"该不该把这批调用一起
并发跑"这个调度层面的问题。

# Solution

给 `Tool` 增加一个布尔类属性 `concurrency_safe`，默认 `False`（未声明即
视为不安全）。只读、无共享可变状态的工具声明为 `True`；有副作用或跨调用共
享状态的工具保持默认（不声明即可）。

Agent 执行一批 tool_calls 时，按模型给出的原始顺序做"分段"：连续的
`concurrency_safe=True` 工具调用归为一段，段内用现有的 `ThreadPoolExecutor`
并发执行；遇到一个不安全的调用，单独成一段，段内串行执行（即使这一段里有多
个不安全调用，也按原始顺序一个个跑，不并发）。段与段之间按原始出现顺序前后
执行，保证不安全操作前后的因果顺序不会被并发打乱。

这不改变对外可见的返回值结构（仍然是与 tool_calls 一一对应、按原始顺序排列
的结果列表），只改变内部的执行调度方式。

# User Stories

1. 作为 Agent 的使用者，当模型在同一轮请求多个只读工具调用（如同时
   `read_file` 三个不同文件），我希望它们并发执行，减少总耗时。
2. 作为 Agent 的使用者，当模型在同一轮请求多个 `bash` 调用，我希望它们按
   原始顺序串行执行，避免因并发导致的 cwd 竞态或输出交错。
3. 作为 Agent 的使用者，当模型在同一轮混合请求只读工具和写工具（例如先
   `read_file` 再 `write_file`），我希望写操作不会在读操作还没完成前提前
   跑，也不希望两类操作被强行拆成大量小批次导致吞吐下降。
4. 作为工具开发者，当我实现一个新工具且不做任何声明时，我希望它默认被当作
   不安全工具串行执行，而不是默认并发——这样我不会因为忘记声明而引入难以复
   现的竞态 bug。
5. 作为工具开发者，当我确认自己的工具是纯读取、无共享可变状态时，我希望能
   显式声明 `concurrency_safe = True`，让调度器把它纳入并发段。
6. 作为 CoreCoder 维护者，当第三方或未来新增的工具没有明确审查过并发安全
   性时，我希望默认行为是"不并发"，而不是需要每个新工具都被显式标记为不安
   全才安全——防止遗漏审查导致静默的并发风险。
7. 作为 CoreCoder 维护者，当同一批 tool_calls 里不安全调用穿插出现（例如
   读-写-读-写），我希望调度结果里每一段的内部执行顺序、段与段之间的顺序都
   严格等于模型给出的原始 tool_calls 顺序，方便调试和结果对照。
8. 作为 Agent 的使用者，当 `agent`（子 agent 工具）被并发调用多次时，我希
   望它们不会被当作并发安全工具处理，因为子 agent 内部可能触发写操作或消耗
   共享的预算/降级状态。

# Implementation Decisions

- `Tool` 增加类属性 `concurrency_safe: bool = False`；子类不声明即继承
  `False`。
- 内置工具中，只有纯只读、无共享可变状态的文件系统查询工具声明为
  `concurrency_safe = True`；`bash` 与子 agent 工具永久保持默认（不安全），
  不通过解析命令前缀或白名单命令的方式尝试细化 `bash` 的安全性——命令解析
  容易被绕过，且与"默认拒绝"的整体思路相悖。
- 调度算法为"分段调度"：对一批 tool_calls 按原始顺序扫描，把连续的安全调
  用聚合成一个并发段，把每个不安全调用单独作为一个串行段；按分段的原始出现
  顺序依次执行各段，安全段内部复用现有的线程池并发执行方式。
- 单个工具调用（`len(tool_calls) == 1`）的处理路径不变。
- 该属性只影响调度方式，不影响工具的输入校验、错误处理或返回值格式。
- 后续如果需要放开 `bash` 或其他工具的并发安全性，应作为单独的决策重新评
  估，不在本次范围内预留开关或配置项。

# Testing Decisions

复用现有测试套件的风格：直接构造 `Agent`（用 `LLM.__new__(LLM)` 或等价
方式跳过真实网络依赖），传入一组自定义的假 `Tool` 子类实例，这些假工具的
`execute()` 记录被调用的顺序、线程 id 或调用时间戳；然后直接调用 Agent 上
负责执行一批 tool_calls 的方法，断言：
- 全部声明为 `concurrency_safe = True` 的连续调用确实发生在不同线程/存在
  时间重叠；
- 未声明（默认不安全）的调用及穿插在安全调用之间的不安全调用，严格按原始
  顺序一个个执行，且不与其他调用发生时间重叠；
- 最终返回的结果列表顺序始终与传入的 tool_calls 顺序一致，无论内部如何分
  段执行。

不引入新的测试框架、不新增端到端/真实进程级别的并发测试。

# Out of Scope

- 不为 `bash` 引入任何形式的命令解析、白名单或沙箱化的"部分并发安全"判定。
- 不改变工具的返回值格式、错误处理方式或输入校验逻辑。
- 不实现"用户/配置可覆盖某个工具的 `concurrency_safe` 默认值"的机制。
- 不涉及降级链、预算上限或 MCP 相关的任何逻辑（见另外两份 spec）。
