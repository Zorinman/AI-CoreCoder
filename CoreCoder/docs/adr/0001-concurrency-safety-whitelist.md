# 并发安全采用白名单默认拒绝，而非黑名单默认允许

> **状态**：已实施并归档
>
> **关联 Spec**：[0001-concurrency-scheduling](../specs/0001-concurrency-scheduling.md)
>
> **实现提交**：`d8a25c4`（2026-08-08）
>
> **归档日期**：2026-08-09

`Tool` 新增 `concurrency_safe: bool = False` 属性，未显式声明的工具默认视为不安全（不可并发）。只有 `read_file`、`glob`、`grep` 三个只读且无外部副作用的工具显式声明为 `True`；`bash`、`agent`（子 agent）无法被静态判定安全性——`bash` 能执行任意命令，`agent` 内部行为对外不透明——因此永远归入不安全类，不做命令前缀解析等黑名单式判断。

同一批 `tool_calls` 按模型给出的原始顺序切分成"连续安全段"和"单个不安全段"，段内并发、段间按原始顺序串行执行，而不是把整批工具粗分成"安全组"和"不安全组"分别打包并发/串行。这保证了模型给出的调用顺序中安全与不安全操作交替出现时的因果关系不被打乱（例如 `write_B` 依赖 `read_A` 已完成的语义仍然成立）。

这是难以逆转的默认值选择：一旦有第三方工具作者习惯了"不声明就是安全"，反转默认值会导致既有工具在未经审查的情况下突然被并发执行，属于静默的安全回退。选择默认不安全，是为了让新增工具的作者必须主动做出"我确认这是安全的"这一动作。
