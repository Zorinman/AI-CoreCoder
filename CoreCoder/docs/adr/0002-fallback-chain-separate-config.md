# 备用模型链用独立配置文件而非环境变量，主模型配置不受影响

`corecoder.fallback.json` 放在项目根目录，只列降级链 `fallback[1..N]`，每一级是完整独立的 `{model, provider, api_key_env, base_url}`（`api_key_env` 存环境变量名，不存密钥明文），不包含主模型。主模型仍完全由 `config.py`/环境变量决定，两套配置来源职责分离。

选择独立 JSON 文件而不是环境变量表达（如 `CORECODER_FALLBACK_MODELS` 用分隔符塞多组值），是因为跨 provider 的降级链本质是结构化的多条目配置，环境变量的扁平字符串表达可读性和可维护性都差，且已经有 `.mcp.json` 的先例证明这类"cwd 下固定文件名自动发现"的配置风格在本项目是可接受的。

熔断逻辑放在新模块 `corecoder/fallback.py`（`ModelChain` 类），不侵入 `llm.py`。主模型重试耗尽（`_call_with_retry` 3 次失败）后触发降级，每一级同样重试 3 次失败才继续降级；全部试完仍失败则抛出明确异常，不回退到链头重试，避免无限循环。降级成功后，本进程剩余生命周期内固定使用该级别（熔断），直到用户用 `/model` 显式指定新模型（此操作重置熔断状态，但新模型仍复用同一条 `fallback.json` 链）。

这个决定的代价：token/成本统计必须从"单模型累计"改为"按模型分组累计"（`llm.py` 的 `estimated_cost` 改动较大），否则降级前的 token 会被降级后模型的单价错误重新定价，与"硬预算上限必须准确"的另一项决定直接冲突。
