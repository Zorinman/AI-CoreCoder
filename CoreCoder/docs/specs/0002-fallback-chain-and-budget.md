# Problem Statement

CoreCoder 目前只有单一主模型配置（`config.py`/环境变量）和针对单次请求的
指数退避重试（`_call_with_retry`，429/超时/连接错误/5xx，最多 3 次）。一
旦主模型的重试全部耗尽，或者用户希望限制单次进程运行的总花费，都没有任何
现成机制：请求会直接以异常失败，也没有任何地方会因为花费超出预期而主动拒
绝继续调用模型。这两项能力在文档中被明确标注为"有意未提供"，原因是会引入
服务商专属逻辑；但生产部署迟早需要补上。

同时，`llm.py` 当前的 token/成本统计（`total_prompt_tokens`、
`total_completion_tokens`、`estimated_cost`）是按"当前唯一模型"累计的单一
计数器。一旦引入降级，主模型和降级模型的单价不同，继续用单一计数器会导致
降级前累计的 token 被按降级后模型的单价重新估价，估算结果失真，也会让预算
上限的判断基准不可靠。

# Solution

新增一个降级链机制：主模型的重试全部耗尽后，按顺序尝试项目根目录
`corecoder.fallback.json` 中列出的备用模型配置，每一级同样重试 3 次失败才
继续降级到下一级；全部降级级别都试完仍失败，则抛出明确异常，不回退到链头
重新循环。一旦降级成功，本进程剩余生命周期内固定使用当前生效的降级级别
（熔断），后续对话不再自动回退去重试主模型，除非用户用 `/model` 显式指定
新模型（此操作重置熔断状态，但新模型仍复用同一条降级链）。这部分逻辑放在
新模块，不侵入现有 `llm.py` 的请求/重试代码。

同时把 token/成本统计从"单模型累计"改为"按模型分组累计"，使得每个模型（主
模型和每一级降级模型）各自的 token 用量按各自的单价计算成本，再汇总为总估
算成本。

新增以美元计的硬性预算上限，由环境变量设置。每轮对话发起新的 LLM 请求之前
检查当前累计估算成本是否已超过上限：超过则直接拒绝发起新一轮请求并返回提示
信息，不中断已经在进行中的调用，也不终止进程。当前生效模型不在定价表内、无
法估算成本时，判断放行（fail open），不会因为缺少定价数据而阻塞用户。用户
可以在不重启进程的前提下，通过一个交互命令当场调高预算上限。

子 agent（`agent` 工具生成的子 Agent）与父 Agent 共享同一份降级/熔断状态和
预算累计状态，不会因为把大任务拆成子 agent 调用就绕开预算上限。

# User Stories

1. 作为在生产环境部署 CoreCoder 的用户，当主模型的所有重试都失败后，我希
   望 Agent 自动切换到备用模型继续完成当前任务，而不是直接抛出异常中断对话。
2. 作为用户，当降级链里的某一级备用模型也重试失败，我希望 Agent 继续尝试
   链中的下一级，而不是回到主模型重新开始一轮重试。
3. 作为用户，当降级链的所有级别都失败，我希望得到一个明确的错误，而不是无
   限循环重试。
4. 作为用户，当某次对话触发过一次成功的降级后，我希望后续的对话请求直接使
   用当前生效的降级级别，而不是每次都先重新尝试一遍已知失败的主模型，浪费时
   间和请求配额。
5. 作为用户，当我想强制换回主模型或换到其他模型时，我希望用现有的 `/model`
   命令显式指定，并且这个操作应该清除之前的熔断状态。
6. 作为用户，当我用 `/model` 换了模型后，我希望降级链配置本身不需要重新设
   置——新的当前模型依然复用同一条 `corecoder.fallback.json` 里定义的降级链。
7. 作为运维/成本敏感的用户，我希望能设置一个以美元计的硬性总花费上限，一旦
   单次进程运行的累计估算成本超过这个上限，后续的 LLM 请求会被主动拒绝，而不
   是超支后才发现。
8. 作为用户，当预算已经用尽但我判断这次任务确实需要继续，我希望能在不重启
   进程、不丢失当前会话上下文的情况下，直接把预算上限调高，继续对话。
9. 作为用户，当预算检查触发拒绝时，我希望已经在执行中的工具调用或已经发出
   的请求不会被强行中断，只是不再发起新的一轮 LLM 请求。
10. 作为用户，当我使用的模型不在内置定价表里（无法估算成本）时，我希望预
    算检查不会因此卡住我的对话——没有定价数据时应当放行而不是报错阻塞。
11. 作为用户，当降级发生后，我希望累计成本统计仍然准确——即降级前用主模型
    产生的 token 按主模型单价计费，降级后用备用模型产生的 token 按备用模型单
    价计费，不会互相串价。
12. 作为使用子 agent 功能拆分任务的用户，我希望子 agent 消耗的预算会计入
    父 Agent 的总预算，且子 agent 也会遵守同一个当前生效的降级/熔断状态，而
    不是每个子 agent 各自独立重新走一遍降级流程或拥有独立的预算额度。
13. 作为 CoreCoder 维护者，我希望降级链的配置（`corecoder.fallback.json`）
    与主模型配置（`config.py`/环境变量）来源分离，改动降级链不需要触碰主模
    型的配置代码路径。
14. 作为使用者，我希望降级链配置文件中不会以明文形式保存任何 API key，只
    保存对应的环境变量名，实际密钥仍从环境读取。

# Implementation Decisions

- 新增模块承载降级链逻辑（`ModelChain` 概念），不侵入现有 `llm.py` 的请求
  发起与单次重试代码；`llm.py` 内的改动只限于把单一 token 计数器/成本估算
  改造为按模型分组累计。
- 降级链配置来自项目根目录的固定文件名 `corecoder.fallback.json`，只包含
  降级级别列表，不包含主模型；每一级是完整独立的配置（模型名、provider、
  API key 对应的环境变量名、base_url），可以跨 provider。选择独立文件而非
  环境变量表达一组结构化配置，是因为环境变量的扁平字符串形式在表达"多级、
  跨 provider 的一组配置"时可读性和可维护性差；项目已有 `.mcp.json` 这类
  "cwd 下固定文件名自动发现"的配置风格先例。
- 熔断规则：主模型重试耗尽后触发降级；每一级降级同样走满 3 次重试才继续降
  级到下一级；全部级别耗尽后抛出明确异常，不回退到链头重新循环（避免无限循
  环）。降级成功后，进程剩余生命周期内固定使用该级别，直到用户显式用
  `/model` 指定新模型（此操作重置熔断状态，但复用同一条降级链）。
- token/成本统计从单一计数器改为按模型分组累计（例如一个"模型名 → 该模型
  下的 prompt/completion token 计数"的映射），总估算成本是各模型分组分别按
  各自单价估算后求和。这是硬性要求，不是可选优化：不这样做会导致降级后的估
  算成本用错误单价重新计价。
- 硬预算上限由一个新的环境变量设置（美元金额）；检查时机是每轮 `chat()`
  发起新的 LLM 请求之前，检查当前累计估算成本是否已超过上限。超过则直接返
  回拒绝提示，不发起本轮请求，不中断已经开始的调用，不终止进程。
- 当前生效模型不在内置定价表内（`estimated_cost` 无法计算）时，预算检查放
  行（fail open）。
- CLI 新增一个交互命令，允许用户在不重启进程的前提下当场调高预算上限。
- 子 agent 与父 Agent 共享同一份 `ModelChain`/熔断状态和预算累计状态，而不
  是每个子 agent 各自持有独立实例——防止拆分子任务成为绕开预算上限的手段。

# Testing Decisions

复用现有测试套件的风格（参考 `test_litellm.py` 对假 `LLM`/`LiteLLM` 实例
的直接构造和方法调用方式）：

- 降级链逻辑：直接构造承载降级逻辑的对象，注入若干个假的 LLM-like 对象
  （通过 mock/自定义类模拟"该级别请求必定失败"或"该级别请求会成功"），直接
  调用其请求方法，断言实际调用顺序、失败时是否正确前进到下一级、全部失败时
  是否抛出预期异常、成功后是否记录了当前生效级别（熔断状态）。
- 熔断状态与 `/model`：直接构造对象后手动触发一次成功降级，断言后续调用不
  再尝试主模型；再模拟一次显式换模型操作，断言熔断状态被清除但降级链配置本
  身不变。
- 按模型分组的成本统计：仿照现有 `test_cost_estimation_known_model` /
  `test_cost_estimation_unknown_model` 的直接属性赋值方式，构造带有多个模
  型分组 token 计数的实例，直接读取汇总后的 `estimated_cost` 属性断言结果，
  并验证未知模型分组时该分组被跳过而不是报错。
- 预算上限检查：直接构造 Agent/降级链对象，设置累计成本高于/低于阈值两种
  情况，直接调用负责发起下一轮请求前检查的方法（不需要真实发出网络请求），
  断言超限时返回拒绝提示且不发起请求，未超限时正常放行；再单独测试模型不在
  定价表内时的放行分支。
- 子 agent 共享状态：直接构造父 Agent 和一个子 agent 调用，断言子 agent 使
  用的是父 Agent 同一份降级/预算状态对象（而不是各自新建一份）。

不引入新的测试框架，不做真实网络调用或真实跨 provider 集成测试。

# Out of Scope

- 不实现基于时间窗口（如"每日/每月预算"）的预算统计，只统计单次进程生命周
  期内的累计估算成本。
- 不为降级链引入除"顺序尝试、失败即下一级"之外的更复杂策略（如按延迟/成功
  率动态排序）。
- 不在 `config.py`/环境变量中重复表达降级链配置；降级链只来自
  `corecoder.fallback.json`。
- 不涉及并发调度或 MCP 相关的任何逻辑（见另外两份 spec）。

# Further Notes

本 feature 依赖 [0001-concurrency-scheduling](0001-concurrency-scheduling.md)
中确立的"默认不安全/不并发"惯例：子 agent 工具本身在那份 spec 中已被列为
永久不安全（不并发），这里进一步要求子 agent 与父 Agent 共享降级/预算状态，
两者是一致的设计方向（子 agent 不应绕过父 Agent 的任何安全或成本约束）。
第三份 spec（[0003-mcp-integration](0003-mcp-integration.md)）同样要求子
agent 默认共享父 Agent 的预算/熔断状态，但默认不继承 MCP 工具。对应决策记
录见 `docs/adr/0002-fallback-chain-separate-config.md`，项目词汇见
`CONTEXT.md` 中的"降级链""熔断""硬预算上限"条目。
